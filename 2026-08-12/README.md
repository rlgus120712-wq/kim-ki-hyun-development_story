# 2026-08-12 개발 기록

프론트엔드(Vue 3 + TypeScript + Ant Design Vue) 작업에서, **서비스 신청 에디터의 서식을 잃지 않고 저장·표시**하도록 개선하며 배운 점을 정리한다. 사용자가 리치 텍스트 에디터로 꾸민 신청 내용(굵게·색상·정렬·리스트·줄바꿈)이 타임라인에서 **입력한 그대로** 보이게 하는 것이 목표였다.

---

## 1. 서식이 사라지는 지점은 "렌더"가 아니라 "저장"이었다

타임라인에 신청 내용이 밋밋한 평문으로만 떴다. 처음엔 렌더(표시) 쪽을 의심했지만, 실제 원인은 **저장 시점**이었다.

### 배운 점
- 저장 정규화 함수가 `stripHtml()`로 **모든 태그·엔티티를 제거**하고 개행만 남겨 DB에 넣고 있었다. 즉 서식은 **저장되기도 전에** 날아갔다.
- 렌더는 `v-html`/`innerHTML`이라 서식을 표현할 수 있었는데, **저장값 자체가 이미 평문**이라 보여줄 서식이 없었다.

```ts
// 문제: 저장 시 태그를 다 벗겨 평문으로 만들어 버림
const normalized = stripHtml(rawContent); // <strong>안녕</strong> → "안녕"
```

### 교훈
> 데이터가 "표현이 안 되는" 것과 "애초에 없는" 것은 다르다. 파이프라인을 **저장 → 조회 → 렌더** 순으로 되짚어, 서식이 소실되는 **첫 지점**을 찾는 게 먼저였다.

---

## 2. `stripHtml` vs `sanitizeHtml` — 제거가 아니라 정화

태그를 다 지우는 대신, **위험한 것만 제거하고 서식은 보존**하는 방향으로 바꿨다. DOMPurify를 도입했다.

| 함수 | 하는 일 | 용도 |
|------|---------|------|
| `stripHtml` | 태그·엔티티 전부 제거 → 순수 텍스트 | 길이 계산, 미리보기 요약 |
| `sanitizeHtml` | XSS만 제거, 서식 태그는 **보존** | 저장·렌더 |

```ts
export const sanitizeHtml = (input?: string | null): string => {
  if (!input) return '';
  // 구 데이터(개행만 있는 평문) 하위호환: \n → <br>
  const withBreaks = input.replace(/\n/g, '<br>');
  return DOMPurify.sanitize(withBreaks, {
    ALLOWED_TAGS: ['p','br','span','strong','b','em','i','u','s','ul','ol','li','h1','h2','h3','blockquote','a', /* ... */],
    ALLOWED_ATTR: ['style','class','href','target','rel'], // 색상·정렬(style) 보존
  });
};
```

### 배운 점
- `ALLOWED_TAGS`/`ALLOWED_ATTR` **허용목록(allowlist)** 방식이 안전하다. `style`을 허용해 색상·정렬은 살리되, DOMPurify가 내부 CSS와 `javascript:` 같은 위험 프로토콜은 알아서 걸러준다.
- `\n → <br>` 변환을 sanitize 안에 넣어, **과거에 평문으로 저장된 데이터**도 개행이 유지되도록 하위호환을 챙겼다.

---

## 3. 방어는 한 겹이 아니라 두 겹 — 저장 + 렌더 모두 sanitize

서식을 보존하기로 하면서 `v-html`/`innerHTML`로 사용자 입력 HTML을 그리게 됐다. 여기서 XSS 방어가 중요해졌다.

### 배운 점
- **저장 시 한 번, 렌더 시 한 번** sanitize하는 이중 방어(defense in depth)를 택했다.
  - 저장 측: 정화된 HTML만 DB로.
  - 렌더 측: 혹시 과거에 오염된 데이터가 있어도 화면에 나가기 전 다시 정화.
- "저장 때 정화했으니 렌더는 믿는다"는 위험하다. **신뢰 경계(trust boundary)를 넘을 때마다** 정화하는 편이 안전하다.

```ts
// 렌더(타임라인 카드) — vnode로 안전하게 innerHTML 주입
vnode: h('div', {
  class: 'typography-body-2 rich-text-content',
  innerHTML: sanitizeHtml(item.requestContent),
});
```

## 4. "검증"과 "변형"을 분리 — yup `.test()` vs `.transform()`

신청 내용에는 글자 수 제한(최대 400자)이 있었다. 자칫 검증 과정에서 값이 바뀌면 서식이 또 날아갈 뻔했다.

### 배운 점
- yup 스키마에서 길이 검사는 `.test()`로 하고, **`.transform()`은 쓰지 않았다.**
  - `.test()`는 통과 여부(boolean)만 판단 → **원본 값은 그대로**.
  - `.transform()`은 값 자체를 바꿔버림 → 여기에 `stripHtml`을 넣었다면 저장값이 평문이 됐을 것.
- 길이 계산엔 `stripHtml(value)`를 써서 **태그 제외 순수 텍스트 기준**으로 셌다. 덕분에 색상·굵게 태그가 많아도 400자 제한에 억울하게 걸리지 않는다.

```ts
// 저장은 HTML, 카운트는 텍스트 — 관심사를 분리
.test('max-length', '최대 400자', (v) => stripHtml(v ?? '').length <= 400)
// .transform(stripHtml)  ← 이렇게 하면 실제 저장값까지 벗겨진다 (금지)
```

### 교훈
> **검증은 값을 판단만 하고, 바꾸지 않는다.** "글자 수는 텍스트로 세되, 저장은 HTML로" — 카운트 기준과 저장 형식이 다를 수 있음을 분리해서 다뤘다.

---

## 5. 공용 유틸은 배럴로 노출, 소비처는 형식만 안다

`sanitizeHtml`은 공용 라이브러리(`@shared-common`)의 HTML 유틸에 넣고 배럴(`index.ts`)로 재노출했다. 저장 헬퍼·타임라인 위젯·타임라인 아이템 컴포넌트가 **같은 한 함수**를 소비한다.

### 배운 점
- 정화 규칙(허용 태그·속성)을 **한 곳**에 두니, 저장이든 렌더든 정책이 일관된다. 규칙을 바꿀 때도 한 파일만 고치면 된다.
- 소비처는 "이 문자열을 안전한 HTML로 만들어줘"만 알면 되고, **어떤 태그를 허용하는지는 몰라도 된다.** (책임 분리)

---

## 오늘의 한 줄
> "서식이 안 보이면 렌더부터 의심하기 쉽지만, 데이터가 **없는** 것일 수도 있다. 파이프라인의 첫 소실 지점을 찾고 — 저장은 보존하되, 신뢰 경계를 넘을 때마다 정화하자."
