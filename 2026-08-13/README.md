# 2026-08-13 개발 기록

프론트엔드(Vue 3 + TypeScript + Ant Design Vue) 작업에서, **데이터 조회기간(데이트피커) 정책**을 공용 컴포넌트로 추상화하며 배운 점을 정리한다.

---

## 1. "동작"이 아니라 "정책"을 넘긴다 — 데이트피커 정책 객체화

여러 목록 화면이 각자 "시작일/종료일 기본값"을 개별 함수로 계산하고 있었다. 화면마다 기본값·최대 조회기간·프리셋 목록이 조금씩 달라서, 공용 테이블 컴포넌트에 매번 다른 유틸을 꽂는 구조였다.

### 배운 점
- 화면마다 다른 건 **로직이 아니라 값(정책)**이었다. 그래서 동작 대신 **정책 객체 하나**를 넘기도록 바꿨다.

```ts
interface DateFilterPolicy {
  presetSet: 'shortTerm' | 'general' | 'longTerm'; // 프리셋 묶음
  unit: 'day' | 'datetime';                        // 일 단위 vs 시·분·초
  defaultPreset?: DateFilterPresetKey;             // 초기 선택값
  maxSpanDays?: number;                            // 최대 조회 기간
  allowEmpty?: boolean;                            // 전체조회 허용 여부
}
```

- 컴포넌트는 이 정책만 읽어서 표시 포맷(`YYYY-MM-DD` vs `YYYY-MM-DD HH:mm:ss`), 시간 선택 노출, 초기값, 비활성 날짜를 **파생**한다.
- 화면 코드는 "무엇을 원하는지"만 선언한다. **어떻게 계산하는지는 몰라도 된다.**

```ts
const dateFilter = {
  columnKey: 'createdAt',
  policy: {
    presetSet: 'general',
    unit: 'datetime',
    defaultPreset: 'last-30d',
    maxSpanDays: 30,
    allowEmpty: false,
  },
};
```

## 2. 중복 구현이 두 갈래로 갈렸을 때 — SSOT로 수렴

같은 문제를 나와 다른 동료가 **동시에 각자** 구현하고 있었다. 한쪽은 공용 UI 컴포넌트 안에, 다른 쪽은 공용 유틸 라이브러리에 정책 유틸을 올렸다.

### 배운 점
- 두 구현을 합칠 때 **"누구 코드를 살리냐"가 아니라 "어디가 단일 진실 공급원(SSOT)이냐"** 를 먼저 정했다.
- 정책 계산 로직(프리셋 해석, 비활성 날짜 규칙)은 **유틸 라이브러리 한 곳**으로 몰고, UI 컴포넌트는 그걸 **소비만** 하도록 정리했다.
- 결과적으로 파일 충돌 없이, 로직 중복 0으로 합쳐졌다. 각자 만든 코드 중 **하드코딩이 적고 재사용성이 높은 쪽**을 SSOT로 채택.

### 교훈
> 중복 구현을 만나면 지우기 전에 **경계부터 그린다.** "계산은 유틸, 표현은 컴포넌트"처럼 책임을 나누면 양쪽 작업이 자연스럽게 한 곳으로 수렴한다.

## 3. dayjs "오늘" 경계 버그 — `23:59:59`가 끼어드는 문제

시·분·초 단위 화면에서 프리셋 **"오늘"**을 누르면 종료 시각에 `23:59:59`가 들어갔다. 아직 오지 않은 미래 시각이 조회 조건에 포함되는 버그.

### 원인과 해결
- "오늘"을 `[startOf('day'), endOf('day')]`로 잡으면 종료가 **그날 23:59:59**가 된다. 일 단위에선 맞지만, **시·분·초 단위에선 미래**다.
- 단위에 따라 경계를 다르게 계산해야 했다:

```ts
// 일 단위: 하루 전체
today → [startOf('day'), endOf('day')]
// 시·분·초 단위: 지금까지
today → [startOf('day'), now]
```

- 추가로 캘린더 자체에서 **미래 날짜·시각을 못 고르게** `disabled-date` / `disabled-time`을 정책 단위 기준으로 걸었다.

### 교훈
> "오늘"은 **단위에 따라 의미가 다르다.** 일 단위의 오늘은 하루 전체, 초 단위의 오늘은 "지금까지"다. 경계값은 항상 단위와 함께 생각한다.

## 4. 최대 조회기간 — 롤링 윈도우 vs 앵커 기준

`maxSpanDays: 30`을 "최근 30일"로만 해석하면, 사용자가 시작일을 과거로 옮겼을 때 종료일 제한이 애매해진다.

### 배운 점
- 최대 기간은 **고정된 최근 N일(롤링)**이 아니라, **사용자가 먼저 찍은 날짜(앵커) 기준 ±N일**로 잡아야 자연스럽다.
- 한쪽 날짜를 선택하면 그 앵커를 저장해두고, 반대쪽에서 고를 수 있는 범위를 `앵커 ± maxSpanDays`로 비활성 처리.
- "포함 N일(inclusive)" 계산에 주의: 3일 최대면 시작일 포함 3일이라 `+2일`까지 허용이다. off-by-one이 나기 쉬운 지점.

## 5. 하위호환은 opt-in으로 — 회귀 없이 점진 도입

정책을 안 넘긴 기존 화면들이 깨지면 안 됐다.

### 배운 점
- 새 로직을 **`policy` 존재 여부로 게이팅**했다. 정책이 있으면 신규 경로, 없으면 기존(레거시) 동작 그대로.
- 덕분에 화면을 하나씩 옮겨도 나머지는 무영향. **big-bang 마이그레이션 대신 화면 단위 점진 전환**이 가능했다.

```ts
const presets = computed(() =>
  policy.value ? buildPresetsFromPolicy(policy.value) : legacyPresets
);
```

## 6. 자잘한 TypeScript 타입 정리

작업 중 손댄 파일에서 기존 타입 오류들을 함께 정리했다.

- **`computed`의 좁은 리터럴 유니온** — `toLowerCase()`는 `string`을 반환해 `'admin' | 'user'`에 안 맞는다. 값이 확실할 땐 `as`로 좁힌다.
  ```ts
  const type = computed(() => props.consoleType.toLowerCase() as 'admin' | 'user');
  ```
- **`ref`는 초기값이 아니라 제네릭으로 타입을 준다** — 초기 객체가 전체 타입의 일부만 담을 때는 `ref<ReqType>({ ... })`로 명시.
- **핸들러 바인딩 타입 불일치** — `@click="btn.onClick"`(옵셔널 함수)이 컴포넌트가 기대하는 시그니처와 안 맞으면 `@click="() => btn.onClick?.()"`로 감싼다.
