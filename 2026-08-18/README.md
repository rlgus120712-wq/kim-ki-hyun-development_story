# 2026-08-18 개발 학습 노트

프론트엔드 개발을 하며 마주치는 일반적인 주제 세 가지를 정리한다. 특정 프로젝트 이야기가 아니라, **어디서든 통하는 원칙**으로 기록한다.

---

## 1. 함수의 "기본 인자"를 착각하지 말자

함수를 호출할 때 넘기는 숫자 인자는, 코드를 훑어보는 것만으로는 그 의미를 오해하기 쉽다.

예를 들어 어떤 포맷 함수가 소수 자릿수를 두 번째 인자로 받고 그 **기본값이 2**라고 하자.

```ts
function formatNumber(value: number, fractionDigits = 2): string {
  return value.toFixed(fractionDigits);
}

formatNumber(3.14159, 1); // "3.1"  ← 명시적으로 1을 넘김
formatNumber(3.14159);    // "3.14" ← 인자 생략 → 기본값 2 적용
```

호출부만 보면 `formatNumber(x)` 쪽이 "기본값"이고 `formatNumber(x, 1)` 쪽이 "특별한 값"처럼 보인다. 하지만 사실은 **정의부의 기본값이 2**이고, `1`을 넘긴 쪽이 그 기본값을 **의도적으로 덮어쓴 것**이다.

두 호출을 같은 표기로 통일하고 싶다면, 명시적으로 넘기던 인자를 지워 기본값으로 수렴시키면 된다.

### 교훈
> 호출부의 인자는 "기본값처럼 보이는 것"과 "실제 기본값"을 헷갈리게 만든다. **한 줄을 고치기 전에 함수 정의의 기본값부터 확인하자.** "왜 이 값이 들어갔지?"라는 질문 하나가 잘못된 수정을 막는다.

## 2. 접근 거부를 403으로 줄까, 404로 줄까

권한이 없는 사용자가 특정 리소스에 접근했을 때 어떤 상태 코드를 주느냐는, 기술 문제가 아니라 **정책 선택**이다.

- **403 Forbidden**: "이 리소스는 존재하지만, 당신은 접근할 수 없다." → 리소스의 **존재 사실이 노출**된다.
- **404 Not Found**: "그런 리소스는 없다." → 존재 여부 자체를 감춘다.

일반 사용자에게 **존재조차 알리고 싶지 않은** 관리자 전용 영역이라면, 403보다 404가 더 안전한 선택일 수 있다. 존재를 알려주는 것만으로도 공격 표면에 대한 힌트를 줄 수 있기 때문이다. (GitHub이 비공개 저장소에 권한 없는 접근을 404로 응답하는 것이 대표적인 예다.)

프런트엔드에서 이 분기를 구현할 때 신경 쓸 점 하나: **판정 로직을 한 곳에 모으고, 조건을 서로 섞지 말 것.** "권한 없음(403)" 조건과 "숨김(404)" 조건이 하나의 변수 안에서 뒤엉키면, "여긴 403인가 404인가"가 모호해지고 그 모호함이 다음 버그가 된다. 별개의 판정은 별개의 조건으로 분리하는 편이 낫다.

### 교훈
> 상태 코드는 "무엇을 알려줄 것인가"라는 정책이다. 그리고 판정 로직은 **같은 레이어에서, 서로 분리된 형태로** 두자. 흩어지거나 뒤섞인 판정이 곧 다음 버그다.

## 3. UI 노출 제어와 서버 검증은 별개의 층이다

사용자가 할 수 없는 작업이 있다면, 두 곳에서 각각 막아야 한다.

1. **서버 검증** — 방어의 최후 보루. UI를 우회한 직접 요청도 막아야 한다.
2. **UI 노출 제어** — 사용자가 애초에 할 수 없는 작업을 화면에 보여주지 않는다.

만약 버튼을 눌러 화면 끝까지 진행했는데 **마지막 실행 단계에서야 권한 오류가 뜬다면**, 그건 서버 방어는 잘 됐다는 뜻이지만 동시에 **UI 게이팅이 빠졌다는 신호**다. 사용자는 할 수 없는 일에 시간을 쓰고 마지막에 거부당하는 헛걸음을 하게 된다.

```html
<!-- 권한이 있을 때만 버튼 자체를 렌더링 -->
<button v-if="canWrite">생성</button>
```

버튼을 조건부로 숨기면 진입 경로 자체가 사라져, 불필요한 실패 토스트도 원천적으로 사라진다. 물론 이것이 서버 검증을 대체하지는 않는다. **둘은 대체 관계가 아니라 보완 관계다.**

### 교훈
> "최종 실행에서 권한 오류가 난다"는 건 UI 게이팅 누락의 신호다. 사용자가 할 수 없는 일은 **버튼 단계에서** 보이지 않게 하고, 서버 검증은 그와 별개로 항상 유지한다.

## 오늘의 한 줄 회고

세 가지 모두 결국 **"증상 뒤의 의도와 원인을 먼저 읽는 일"** 이었다.
- 인자 하나: 기본값인지 오버라이드인지 정의부를 읽어야 옳은 수정이 나온다.
- 상태 코드: "오류"가 아니라 "무엇을 알릴 것인가"라는 정책으로 읽어야 방향이 잡힌다.
- 실패 토스트: 증상이 아니라 "게이팅 누락"이라는 원인을 읽어야 근본 수정이 된다.

> 코드를 고치기 전에, **왜 지금 이렇게 되어 있는지**를 먼저 읽는다.
