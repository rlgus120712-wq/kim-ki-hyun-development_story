# 2026-09-07 개발 학습 노트

AI 에이전트에 도구(tool)를 붙이는 작업을 하며, 기능 인벤토리를 전수 조사하고 갭 분석을 했다. 오늘도 특정 프로젝트 이야기가 아니라 **어디서든 통하는 원칙**으로 기록한다.

---

## 1. "구현됨"과 "사용 가능함"은 다르다

코드베이스에 함수가 존재한다고 해서 시스템이 그 기능을 쓸 수 있는 것은 아니다. 도구가 실제로 동작하려면 보통 여러 지점을 통과해야 한다.

```
정의(코드) → 등록(레지스트리) → 배정(라우팅) → 노출(서버/게이트웨이)
```

오늘 확인한 사례에서는 도구가 정의·등록까지는 되어 있었지만, **라우팅 배정 목록과 노출 서버의 import 목록 두 곳에서 똑같이 빠져** 있었다. 흥미로운 건 에러가 단 한 번도 나지 않았다는 점이다. 연결 지점이 여러 곳에 **수동으로 중복 정의**되어 있으면, 한 곳을 빠뜨려도 시스템은 조용히 "그 기능이 없는 것처럼" 동작한다.

```python
# 안티패턴: 같은 목록을 세 곳에서 각각 수동 관리
ALL_TOOLS   = (A_TOOLS + B_TOOLS + C_TOOLS)          # 등록부
agent.tools = [*A_TOOLS, *B_TOOLS]                    # 배정부 — C가 빠져도 에러 없음
server_expose(A_TOOLS, B_TOOLS)                       # 노출부 — 여기도 C 누락
```

해결 방향은 두 가지다.

1. **단일 소스에서 파생시키기** — 그룹 목록을 한 곳에 두고, 배정부·노출부가 같은 매핑 테이블을 참조하게 한다.
2. **드리프트를 CI로 강제하기** — "정의됐지만 등록 안 됨"을 사람 눈이 아니라 검사 스크립트가 잡게 한다. 검사가 있어도 CI 게이트로 강제되지 않으면 결국 어긋난다.

### 교훈
> 조용한 누락은 수동 중복 정의의 필연이다. **"한 곳을 고치면 나머지가 따라오는가?"** — 아니라면 그 구조는 언젠가 어긋난 채로 운영된다.

## 2. 갭 분석은 "제공자 스펙"이 아니라 "소비자 코드" 기준으로

"어떤 기능이 빠졌는가"를 조사할 때 서버 API 명세부터 뒤지기 쉽다. 그런데 명세에는 아무도 안 쓰는 API와 폐기 예정 API가 섞여 있다. 오늘은 반대로 **실제 화면(프런트엔드)이 호출하는 오퍼레이션을 전수 조사**해서 기준 목록을 만들었고, 이게 훨씬 정확한 "진짜 쓰이는 표면"이 됐다.

이 방식의 부수 효과가 둘 있었다.

- **인상과 실측이 달랐다.** "거의 구현 안 되어 있다"는 팀의 인식과 달리, 실측해 보니 쓰기 기능까지 상당수 구현되어 있었다. 진짜 문제는 양이 아니라 1번에서 말한 연결 누락이었다. 측정 없이 인상만으로 계획을 세웠다면 이미 있는 걸 다시 만들 뻔했다.
- **불일치가 드러났다.** 같은 기능인데 소비자와 제공 도구가 서로 다른 경로를 호출하는 케이스가 몇 건 나왔다. 스펙만 봤다면 "구현됨"으로 넘어갔을 항목이다.

단, 이 방식의 한계도 기록해 둔다. 소비자 기준 조사는 **소비자가 안 쓰는 기능을 놓친다.** 그래서 "이 목록이 전부인가?"는 제공자 쪽 리뷰로 교차 검증해야 완결된다. 그리고 정적 분석으로 "정의됨"을 세는 것과 실제 호출이 성공하는지는 별개다 — 실동작 검증은 남은 숙제로 명시했다.

### 교훈
> 인벤토리는 **실제 호출 지점에서 역산**하고, 한계(미커버 영역·미검증 항목)를 목록에 같이 적는다. "다 조사했다"보다 "여기까지 조사했고 여긴 안 봤다"가 더 쓸모 있는 산출물이다.

## 3. AI 에이전트에게 쓰기 도구를 줄 때의 3중 안전장치

에이전트가 호출하는 도구는 조회(Read)와 변경(Write)의 위험도가 완전히 다르다. 오늘 정리하며 굳어진 원칙:

1. **파괴적 도구는 사람 승인(HITL)을 기본값으로.** 생성 계열만 승인 대상으로 지정하고 삭제·강제 변경 계열이 미분류로 남아 있는 상태가 제일 위험하다. "등록 안 된 도구는 승인 게이트 밖"이라는 점이 1번의 조용한 누락과 결합하면 최악이 된다.
2. **응답은 질의자의 권한 범위로 잘라서.** 관리자 API를 그대로 래핑한 조회 도구는, 묻는 사람이 누구든 관리자 시야로 답하게 된다. 도구 스스로 "질의자가 볼 수 있는 범위"로 응답을 제한해야 한다.
3. **집계는 명시적 집계값으로.** 페이징 응답의 `items` 길이를 전체 건수로 해석하는 실수는 사람보다 LLM이 더 잘 저지른다. `totalCount` 같은 명시적 집계 필드를 우선 사용하고, 없으면 "현재 페이지 기준"임을 밝히도록 에이전트 지침에 박아 둔다.

### 교훈
> 에이전트 도구 설계는 기능 목록보다 **권한 경계 설계**가 먼저다. "무엇을 할 수 있나"만큼 "누구의 자격으로, 어디까지 보이게, 누구 승인 하에"를 정의해야 한다.

## 오늘의 한 줄 회고

오늘 하루의 공통 주제는 **"존재와 가용은 다르고, 인상과 실측도 다르다"** 였다.

- 코드가 있어도 연결이 없으면 기능은 없는 것이다.
- "거의 안 되어 있다"는 말은 세어 보기 전까지는 가설일 뿐이다.
- 그리고 보고할 때는 함수 목록이 아니라 **"사용자가 무엇을 물어볼 수 있게 되는가"** 로 번역해야 전달된다 — 기술 인벤토리와 이해관계자 보고는 같은 데이터의 다른 투영이다.

> 정리하기 전에 세고, 세기 전에 기준(소비자? 제공자?)을 정한다.
