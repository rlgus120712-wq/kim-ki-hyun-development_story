# 2026-09-08 개발 학습 노트

오전에는 워크플로우 기반 관리 화면을 HTML 목업으로 5가지 UI 버전까지 확장했고, 오후에는 권한 회수 시나리오에서 터지는 403 연쇄와 토스트 누락 버그를 잡았다. 오늘도 특정 프로젝트 이야기가 아니라 **어디서든 통하는 원칙**으로 기록한다.

---

## 1. 디자인 비교는 "버전"이 아니라 "축"으로 한다

관리자가 신청 서비스를 조립하는 빌더 화면을 놓고 UI 방향을 정해야 했다. 처음에는 "A안 vs B안"으로 통짜 비교를 하려 했는데, 버전을 늘려 보니 사실 서로 독립적인 **설계 축**들이 섞여 있었다.

| 축 | 선택지 예시 |
|---|---|
| 테마/톤 | 라이트 업무형 / 다크 콘솔 / 소비자 포털 |
| 정보 구조 | 메뉴 분리 / 통합 검색 단일 입구 |
| 워크플로우 시각화 | 가로 카드 레일 / 세로 타임라인 / 캔버스+곡선 / 그래프 / 코드(YAML)↔다이어그램 |
| 입력 흐름 | 단계 위저드 / 원페이지 / 한 질문씩 / 커맨드 팔레트 퀵폼 |

축을 분리하고 나면 "v4를 고르자"가 아니라 "IA는 v1, 빌더 시각화는 v4, 입력은 v1"처럼 **축별로 조합**할 수 있다. 리뷰 회의도 "어느 안이 좋아요?"가 아니라 축마다 하나씩 결정하면 끝난다. 통짜 비교는 좋은 부분과 나쁜 부분이 한 몸으로 묶여서 논의가 겉돈다.

부수 교훈 하나. 비교용 컨셉 데모를 만들 때 **대표 시나리오의 기능 패리티는 맞춰야 한다.** 오늘 "다른 버전엔 핵심 기능이 하나도 없는데?"라는 피드백을 받았다. 비주얼만 다른 데모는 비교 대상이 아니라 그림일 뿐이다 — 각 버전이 같은 시나리오(생성→발행→신청→추적)를 끝까지 돌 수 있어야 축별 비교가 성립한다.

### 교훈
> 디자인 대안은 통짜 버전이 아니라 **독립적인 설계 축의 조합**으로 관리하라. 그리고 비교안들끼리는 최소한 같은 시나리오를 완주할 수 있어야 비교가 성립한다.

## 2. 빌더 UI의 핵심은 "조립"이 아니라 "파생"이었다

워크플로우 빌더라고 하면 노드를 드래그해서 연결하는 캔버스부터 떠올리기 쉽다. 여러 버전을 만들며 확인한 것은, 승인 흐름처럼 **사실상 선형인 도메인**에서는 자유 조립이 오버엔지니어링이라는 점이다.

대신 이런 원칙으로 수렴했다.

1. **구조는 설정에서 파생된다.** 카드를 추가/삭제하는 대신 "승인 단계 수: 없음/1/2/3"을 고르면 카드가 자동으로 늘고 준다. 사용자는 구조를 조립하는 게 아니라 몇 가지 선택으로 알맞은 형태를 얻는다.
2. **미리보기는 편집의 결과이지 편집 대상이 아니다.** 상단 카드 체인은 클릭조차 필요 없게 만들고, 아래 폼에 포커스가 가면 해당 카드가 하이라이트로 따라오게 했다. "지금 어디를 만지는지"는 시각으로, 조작은 폼으로.
3. **관리자가 세팅한 문법 그대로 사용자가 본다.** 관리자 빌더의 카드 체인이 사용자 신청 화면의 진행 카드, 추적 화면의 상태 카드로 그대로 이어지면 학습 비용이 한 번으로 끝난다.
4. **"없음"도 상태다.** 승인 없음을 카드 삭제로 표현하면 다시 켤 입구가 사라진다. 회색 통과(pass) 카드로 남겨두면 구조가 안정되고 재활성화 동선도 생긴다.

### 교훈
> 도메인이 선형이면 자유 캔버스 대신 **설정 파생형 빌더**가 낫다. 편집 가능한 것(폼)과 파생되는 것(미리보기)의 경계를 명확히 하라.

## 3. mutateAsync는 onSuccess가 끝날 때까지 기다린다

권한 관리 화면에서 관리자가 **자기 자신의 권한을 회수**하면: 저장은 되는데 성공 토스트가 안 뜨고, 콘솔에 403이 쏟아진 뒤에야 화면이 전환되는 버그가 있었다.

원인은 흔한 패턴 안에 있었다.

```ts
// mutation 정의
onSuccess: async () => {
  toast('수정했습니다');
  await queryClient.invalidateQueries({ queryKey: ROOT_KEY }); // ← 루트 키 전체
},

// 호출부
await mutateAsync(payload);   // onSuccess의 await까지 전부 기다린다!
await router.push('/list');
```

TanStack Query의 `mutateAsync`는 **onSuccess가 반환한 promise까지 resolve된 뒤에야** 풀린다. 그래서 루트 쿼리키를 `await invalidateQueries` 하면, 방금 권한이 사라진 사용자의 화면 위에서 활성 쿼리 전부가 refetch(전부 403)되는 걸 다 기다린 다음에야 페이지 이동이 실행된다. 사용자 눈에는 "403 먼저, 전환은 나중"으로 보인다.

수정은 세 가지였다.

1. **invalidate를 기다리지 않는다** (`void queryClient.invalidateQueries(...)`). 토스트 → 화면 전환 → 백그라운드 갱신 순서가 보장된다. 떠나는 페이지의 쿼리는 비활성화되어 재조회 자체가 스킵된다.
2. **권한이 바뀌면 메뉴 데이터도 무효화한다.** 페이지 접근은 라우트 가드가 막아줘도, 캐시된 메뉴 트리에는 회수된 메뉴가 계속 보인다. "눌러야 403"이 아니라 "메뉴 자체가 사라짐"이 맞는 UX다.
3. **쓰기 요청 자체가 403으로 떨어지는 레이스를 별도 처리한다.** 권한 회수가 응답보다 먼저 발효되면 "변경은 적용됐는데 응답은 403"이 될 수 있다. 이때 프론트는 성공을 단정할 수 없으므로, 일반 오류로 뭉개지 말고 "권한이 변경되어 결과를 확인할 수 없습니다" 같은 전용 안내로 분기했다.

이 버그의 본질은 예외 케이스 누락이 아니다. **자기 권한 회수는 권한 관리 기능의 정규 시나리오**인데, 성공 경로의 코드가 "요청자는 계속 권한이 있다"를 암묵 전제하고 있었던 것이다.

### 교훈
> `await mutateAsync`는 onSuccess의 비동기 작업까지 통째로 기다린다 — 성공 피드백과 캐시 갱신을 한 promise에 묶지 마라. 그리고 권한 시스템에서 "요청자 자신의 권한이 이 요청으로 사라진다"는 엣지가 아니라 설계해야 할 1급 시나리오다.
