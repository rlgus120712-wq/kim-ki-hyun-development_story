# 2026-09-18 개발 학습 노트

오늘은 코드를 짠 날이 아니라 **git 히스토리를 계량한 날**이다. "운영 중인 레포를 다른 레포의 최신으로 강제로 엎어치겠다, 각자 작업분은 로컬에 받아두라"는 공지를 받고, 실제로 뭐가 어떻게 위험한지 두 레포를 직접 비교하며 분석했다. 오늘도 특정 프로젝트 이야기가 아니라 **어디서든 통하는 원칙**으로 기록한다.

---

## 1. 막연한 불안은 rev-list 숫자로 바꾼다

"엎어치면 문제가 많을 것 같다"는 직감으로 시작했지만, 직감은 대응의 규모를 정해주지 못한다. 그래서 두 레포의 실제 차이를 측정했다. 핵심은 **remote를 등록하지 않고도 로컬 경로로 일회성 비교**가 된다는 것.

```bash
# 다른 레포의 브랜치를 FETCH_HEAD로 한 번만 가져온다 (remote 추가 불필요)
git fetch ../other-repo refs/remotes/origin/dev

# 우리 dev에만 있는 커밋 수 (= 엎어치면 사라질 것들)
git rev-list --count origin/dev --not FETCH_HEAD

# 반대 방향 (= 엎어치면 새로 들어올 것들)
git rev-list --count FETCH_HEAD --not origin/dev

# 공통 조상이 있는지 — 히스토리가 이어져 있는지 단절인지
git merge-base origin/dev FETCH_HEAD
```

결과는 예상과 달랐다. 유실 위험 커밋은 **단 1개**, 두 브랜치는 공통 조상을 공유하고 있었고, 릴리즈 브랜치는 아예 완전한 부분집합이라 잃을 게 없었다. "문제가 많을 것"이라는 불안이 "커밋 1개 + 한쪽에만 있는 브랜치 9개"라는 구체적 목록으로 바뀌자, 대응도 "그 커밋 포팅 여부 확인 + 브랜치 범위 질문"으로 좁혀졌다.

### 교훈
> 히스토리 리스크는 형용사("많이 꼬일 듯")가 아니라 `rev-list --count`의 숫자로 말하라. 측정 전의 불안과 측정 후의 대응은 규모가 완전히 다르다.

---

## 2. "각자 로컬에 받아두세요"는 백업 전략이 아니다

강제 덮어쓰기 전에 "작업분은 각자 로컬에 받아두라"는 안내가 나왔다. 선의의 안내지만, 이 방식은 **팀원 전원이 공지를 보고 → 이해하고 → 제때 행동한다**는 세 가지 가정 위에 서 있다. 공지를 놓친 사람, 휴가자, 의미를 다르게 해석한 사람은 그대로 유실이다.

올바른 방법은 리스크를 개인에게 분산시키지 않는 것이다.

```bash
# 엎기 직전, 서버 쪽에서 5초면 끝난다
git branch backup/dev-YYMMDD origin/dev && git push origin backup/dev-YYMMDD
# 또는 태그
git tag archive/dev-YYMMDD origin/dev && git push origin --tags
```

서버에 ref 하나만 남기면 전원의 백업이 한 번에 끝나고, 나중에 "그때 그 커밋"을 찾는 것도 reflog 고고학이 아니라 브랜치 체크아웃이 된다.

또 하나, 공지에서 빠지기 쉬운 것이 **범위**다. "dev를 엎는다"와 "레포 전체를 미러로 덮는다"는 피해가 완전히 다르다. 비교해 보니 대상 레포에만 존재하는 feature 브랜치가 9개 있었는데, 전체 미러링이라면 이것들이 통째로 사라진다. "dev 작업분 받아두세요"라는 문장만으로는 이 브랜치들의 운명을 알 수 없다.

### 교훈
> 백업은 개인의 기억이 아니라 서버의 ref로 남겨라. 그리고 파괴적 작업 공지에는 반드시 **범위**(어느 브랜치까지인가)와 **시점**(freeze는 언제부터인가)이 명시되어야 한다.

## 3. force push는 push로 끝나지 않는다 — 좀비 히스토리

공유 브랜치의 히스토리를 재작성하면, 그 순간부터 팀원 전원의 로컬 브랜치가 새 히스토리와 갈라진다. 여기서 가장 흔한 사고 패턴:

1. 누군가 옛 히스토리 기반 로컬에서 습관적으로 `git pull`
2. git이 옛 히스토리와 새 히스토리를 **merge**해 버림
3. 그걸 push하는 순간 **엎어치기 전 코드가 통째로 부활** (좀비 히스토리)

엎은 의미가 무효화되는 것이다. 그래서 force push 공지에는 전원이 해야 할 로컬 절차가 함께 가야 한다.

```bash
git fetch
git switch dev
git reset --hard origin/dev   # pull 금지, reset으로 갈아탄다
```

파생 작업들도 마찬가지다. 옛 브랜치에서 딴 feature 브랜치는 `rebase --onto`로 새 기준점 위로 옮기지 않으면 MR diff가 수천 줄로 부풀고, 열려 있던 MR은 기준 커밋이 사라지며 리뷰 코멘트가 앵커를 잃는다. 활성 레포라면 공지와 실행 사이에도 커밋은 계속 쌓이므로, **실행 직전에 diff를 재측정**하는 것까지가 한 작업이다.

### 교훈
> 히스토리 재작성은 "push 성공"이 아니라 "팀 전원의 로컬이 새 히스토리로 갈아탄 것"까지가 완료 조건이다. `pull` 한 번이 전체 작업을 무효화할 수 있다.

---

## 오늘의 한 줄

> 불안은 rev-list로 계량하고, 백업은 서버 ref로 남기고, 엎어치기는 전원의 reset까지가 한 작업이다.
